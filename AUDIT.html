ElevateCRM Test Audit

Date 28 Aug 2026 Branch main @ dfb2b47 Stack Express + MongoDB / React + Vite Suites Jest + Supertest, Playwright App code changed none

A full automated test suite was written for the backend API and the frontend application, and then run against them. Both suites pass. Building them surfaced eight defects in the application, three of which affect data the product is responsible for keeping.

Headline

Dragging a deal between pipeline stages never saves. The card moves on screen, no request is sent to the server, and the change is gone on the next reload. The pipeline is the product's headline feature and nothing in the interaction hints that the move was discarded. Reproduced deterministically; root cause identified in usePipelineDrag.ts. See F-01.

How the defects are recorded

Every finding below is pinned by a live test, not just described in prose.

Backend defects use Jest's it.failing; frontend defects use Playwright's test.fail(). Both invert the result: the test passes while the assertion fails, and starts failing the moment the bug is fixed. That keeps the suite green today while making it impossible to ship a fix without being told the marker is now stale — delete the marker, keep the assertion, and the test becomes an ordinary regression guard.

No application code was modified. The brief was tests only, with defects flagged rather than fixed. Everything added is test code, test support, or documentation: backend/tests/, backend/jest.config.js, e2e/, playwright.config.ts, frontend/vite.e2e.config.ts, TESTING.md. Three devDependencies blocks gained test packages.

Findings

Ranked by severity. Each was reproduced before being reported.

Critical F-01 Frontend

Pipeline stage moves are silently discarded

Where
frontend/src/hooks/usePipelineDrag.ts — onDragOver / onDragEnd
Mechanism

onDragOver optimistically writes the target stage into the React Query cache while the pointer is still down. onDragEnd then recomputes original from deals — which is derived from that same, already-mutated cache — and returns early on targetStage === original.stage. For a real move that comparison is always true, so move() is never called and no HTTP request is issued at all.

Impact

The board looks correct until the deals query is refetched or the page reloaded, at which point every card snaps back. Downstream, a deal can never reach Won by dragging, so the Won → Contact conversion never fires and no customer record is created. Sales data entered through the primary interface is lost without any error.

Evidence

Observed live: card moves Lead → Qualified in the DOM, PATCH requests: [], and after reload the card is back in Lead. The server endpoint itself is fine — 63 backend tests cover PATCH /api/deals/:id/stage including the Won hook.

Pinned by e2e/lead-lifecycle.spec.ts → "a dragged stage move should persist", "dragging a deal to Won should create a Contact".

Suggested fix

Capture the deal's stage in onDragStart and compare against that snapshot in onDragEnd, rather than re-reading the cache the drag has already mutated.

High F-02 Backend · tenancy

Cross-tenant data leak through unvalidated references

Where
controllers/tasks.controller.js, deals.controller.js, contacts.controller.js, leads.controller.js
Mechanism

No create or update handler checks that an incoming reference — assignedTo, relatedTo, leadId, dealId — points at a record in the caller's own organization. The handlers then .populate() those references, and populate resolves by _id alone with no tenancy filter. A user in Org A who supplies an Org B ObjectId gets that foreign record's fields echoed back — in the create response, and again on every subsequent list request.

Impact

Confirmed leaks: a foreign lead's first name, last name and company (via a task's relatedTo or a deal's leadId); a foreign user's first name, last name, email and avatar (via assignedTo). The reference persists in the document, so it re-leaks on every read until removed. Exploitation requires knowing a target ObjectId, which bounds it — but ObjectIds are exposed in URLs and are partly timestamp-derived, and this is a tenancy boundary, where the bound is not the point.

Evidence

Pinned by backend/tests/multitenancy.test.js → 5 markers under "KNOWN GAP: cross-tenant reference population". Everything else about the boundary holds: 200 tests in that file cover reads, writes, deletes, lists, counts, search, filters, pagination and aggregates across Leads, Deals, Contacts, Tasks, Team members, Invitations and Organization, for all five roles, in both directions.

Suggested fix

Validate each reference at write time against the caller's organizationId and reject with 400 — filtering on read would leave a dangling cross-tenant pointer that a future populate resolves again.

High F-03 Backend · auth

Refresh tokens are not unique, so sessions die at random

Where
services/token.service.js — generateRefreshToken services/auth.service.js — buildTokenPair
Mechanism

generateRefreshToken is always handed exactly { sub }. The only other fields in the JWT are iat, exp and iss, and iat/exp have one-second resolution — so any two refresh tokens issued to the same user inside the same second are byte-identical, and their stored SHA-256 hashes collide.

Rotation then eats itself: refresh #1 revokes the old row and inserts a new row with the same hash, so refresh #2 finds the revoked row first and returns 401. Separately, two logins in one second create two rows sharing one hash, and revokeRefreshToken uses updateOne, so logout revokes only one of them.

Impact

A 401 from /auth/refresh clears the client session. Every full page load re-bootstraps with a refresh call, so navigating quickly by URL — or simply having two tabs open, since each tab's isRefreshing guard is per-tab — logs the user out. This reads as flaky, unexplained sign-outs, which is the hardest class of bug to get a useful report about.

Evidence

Pinned by backend/tests/auth.test.js → 4 markers under "KNOWN GAP: refresh token uniqueness", and independently reproduced from the browser by e2e/auth.spec.ts → "rapid full-page navigation signs the user out". Seen in the API log as a run of POST /api/auth/refresh 200 with a 401 in the middle and the app back on the login screen.

Suggested fix

Add a random jti (or any nonce) to the refresh payload. That one change resolves all four markers and the E2E symptom.

Medium F-04 Backend · reporting

closedAt is only stamped by the drag endpoint

Where
controllers/deals.controller.js — updateDeal (PATCH /api/deals/:id)
Mechanism

moveDealStage deliberately uses findOne + save so the pre-save hook fires and stamps closedAt. updateDeal uses findOneAndUpdate, which does not run document middleware — so setting a deal to Won or Lost through the ordinary edit form leaves closedAt null.

Impact

closedAt is the field the money reports key off. A deal won this way is absent from weekly revenue, from the revenue-trend buckets, and from the activity feed, while showing as Won everywhere else. It presents as "the dashboard numbers are wrong", not as a stage bug. reports.service.js already carries a comment working around exactly this; dashboard.service.js does not.

Evidence

Pinned by backend/tests/deals.test.js → 5 markers under "KNOWN GAP: closedAt on PATCH /api/deals/:id", including assertions through /api/dashboard/stats, /api/dashboard/revenue-trend and /api/activity-log. A passing test sits alongside them confirming the /stage route does stamp it, so the gap cannot be misread as "closedAt never works".

Medium F-05 Frontend

A newly added lead does not appear in the table

Where
frontend/src/components/leads/AddLeadDrawer.tsx — createLeadMutation.onSuccess
Mechanism

The drawer declares its own useMutation and invalidates only ['dashboard','stats'] and ['dashboard','lead-activity']. It never invalidates ['leads'], which is the key useLeadsList reads — and that query sets staleTime: 2 * 60 * 1000. The repository already contains a useCreateLead hook that invalidates ['leads'] correctly; the drawer does not use it.

Impact

The user sees "Lead added successfully" and an unchanged table. The record can stay invisible for up to two minutes, and navigating away and back does not help. The obvious reading is that the save failed, so people re-enter the lead.

Evidence

Pinned by e2e/lead-lifecycle.spec.ts → "a newly added lead should appear without a reload". A companion passing test confirms the record really is persisted.

Medium F-06 Frontend

Registration dead-ends on the login page with no message

Where
frontend/src/pages/auth/RegisterPage.tsx — registerMutation.onSuccess
Mechanism

onSuccess discards the entire response. The API returns { user, organization, tokens } and sets a refresh cookie, but the mutation calls neither setAuth nor anything else — it only navigates to /verify-email. That page's first branch is if (!isAuthenticated && !token) return <Navigate to={LOGIN} />, so the brand-new user is bounced straight to the login screen.

Impact

A person fills in the sign-up form, clicks Create Account, and lands on the login page with no confirmation, no "check your inbox", and no resend button — the account exists and the email was sent, but nothing says so. The entire "Check your inbox" screen, including its resend-verification control, is unreachable from registration. The tokens the server issued are thrown away.

Evidence

Pinned by e2e/auth.spec.ts → 'after registering, the user should see "Check your inbox"'. The rest of the journey works: the same spec registers, reads the real verification token, verifies through the real endpoint, logs in, and loads the dashboard.

Low F-07 Frontend

Every failed login reports "No refresh token provided"

Where
frontend/src/services/api/axiosInstance.ts — response interceptor, 401 branch
Mechanism

The interceptor treats every 401 as an expired access token and fires a silent refresh, with no exemption for the auth endpoints themselves. A failed POST /auth/login (401 INVALID_CREDENTIALS) therefore triggers POST /auth/refresh, which fails with 401 NO_REFRESH_TOKEN because an anonymous visitor has no refresh cookie — and it is that error which reaches login.mutate's onError.

Impact

Users mistyping a password are shown an internal message that tells them nothing. It also masks the real reason: "please verify your email" (a 403) still surfaces correctly, but wrong-password and unknown-account do not. Plus one wasted round-trip on every failed sign-in.

Evidence

Pinned by e2e/auth.spec.ts → "a wrong password should say so, not report a missing refresh token". A companion passing test confirms the login is genuinely refused and no session is created.

Low F-08 Frontend · RBAC

The global header offers "Add Lead" to a viewer

Where
frontend/src/components/layout/TopNavbar.tsx
Mechanism

The header's "Add Lead" button has no permission check at all — no usePermissions, no can(...). LeadsPage gates its own copy of the button correctly on can(LEADS_WRITE); the global nav does not.

Impact

A viewer sees the button on every page, can open the drawer, fill in the whole form, and only discovers the action was never available when the submit answers 403. Not a security hole — the server refuses the write — but the interface promises something it cannot deliver.

Evidence

Pinned by e2e/rbac-ui.spec.ts → "the header offers Add Lead to a viewer". A companion passing test drives the drawer to submission as a viewer and asserts the API returns 403, which is what confirms the boundary itself holds.

What holds up well

Worth saying plainly, because a findings list on its own is misleading.

Tenant isolation

Every controller scopes the query by organizationId rather than fetching and comparing afterwards, so a foreign id matches nothing and the denial is indistinguishable from a missing record — no existence oracle. Counts, searches, aggregates and reports are all scoped. 200 tests, one leak (F-02).

Server-side RBAC

Every guarded route was driven against every role: 213 tests. The owner is protected as a target from demotion and removal, including by themselves and through two separate routes; nobody can act on a peer at or above their own level; the invite level check reads the database role, not the token claim, so a stale token cannot widen it.

Injection and XSS

Operator-injection in login bodies, filters and search is neutralised; regex metacharacters, unbalanced parentheses and a catastrophic-backtracking pattern all return an empty result set rather than a 500 or a hang. Stored payloads round-trip verbatim and are served as JSON with nosniff, so they are inert in transit.

Token handling

Expired, malformed, wrong-secret, wrong-issuer, alg:none and payload-tampered tokens are all 401 with no stack trace. A refresh token cannot be used as an access token. A 2FA temp token is refused everywhere except /auth/verify-otp, and that route refuses full access tokens.

Rate limiting

Login (5 / 15 min), forgot-password and resend-verification (3 / hr) and the general API surface (100 / 15 min) all reach 429. The block applies to the correct password too, buckets per IP rather than per account, and X-Forwarded-For cannot escape it in the shipping configuration.

Responsive layout

No horizontal page scroll and no overlapping text on Dashboard, Leads or Pipeline at 375, 768 or 1280 px — 35 checks, all passing. The kanban board correctly scrolls inside its own container rather than the page. No visual regressions found.

Notes on the brief

Three places where the application does not match what the brief assumed. None is a defect; each changed what got tested.

Member and Team Settings

The brief asks to confirm a Member "cannot access Team Settings". A Member can reach /settings/team, by design — the route carries no role guard, GET /api/team/members is open to any member, and the page degrades to a read-only roster. The settings page that is role-gated is /settings/organization. Both are now asserted for their real behaviour.

Leads are not pipeline cards

The brief describes dragging "the lead" through the pipeline. The board holds Deals; Lead and Deal are separate collections, and it is a Deal reaching Won that creates a Contact. The New Deal dialog also collects no leadId, though the API accepts one — so the two halves of the funnel cannot be joined from the UI, and the Contact that Won produces is named after the deal rather than the person. Worth a product decision.

Password policy disagreement

The client's registration schema requires a special character; the API's passwordRules require only 8 characters, an uppercase letter and a digit. The client being stricter is safe, but the two should agree, or an API-created password will be one the UI would have rejected.

One thing to know about the harness

A near-miss worth recording, and one deliberate trade-off.

Near miss Test infrastructure

The first suite run connected to the live SMTP server

What happened

The test setup originally deleted the SMTP_* variables so the email service would fall back to its console stub. But app.js calls dotenv.config() at require time, and dotenv fills in any key that is missing while skipping one that is already present — so deleting them handed the real backend/.env credentials straight back, and the run authenticated against the production Brevo SMTP server. Log line: ✅ Brevo SMTP connected successfully.

Now

Those variables are set to '' rather than deleted, and tests/setup/afterEnv.js asserts at startup that no real SMTP or Gemini credential is visible to the test process — it refuses to run if one is. Anyone adding an E2E-style harness to this repo should know this: a test suite that boots app.js inherits .env unless it actively blocks it.

Rate limiting is disabled inside the E2E environment, deliberately. A full run is several hundred requests from one machine, which the 100-per-15-minute limiter would refuse, so e2e/rate-limit-proxy.cjs gives every request a distinct X-Forwarded-For and the API runs with TRUST_PROXY=true — the same setting it uses on Render. The header is injected server-side because config/cors.js allows only Content-Type and Authorization from the browser. The limiters themselves are tested directly in security.test.js, including the fact that X-Forwarded-For cannot bypass them in the configuration that ships.
